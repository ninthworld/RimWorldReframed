RimWorld UI Reworked reconstruction specification

Revision 2 · 17 October 2026 · Planning and reference analysis · No new implementation in this revision

The target is a faithful reconstruction of RimWorld UI Reworked by yarich SA. The existing Reframed UI v0.2 prototype is an experiment, not a visual baseline. Completion requires both reference fidelity and correct RimWorld behavior. A recolored vanilla interface does not meet this target.

This specification divides the reference into independent projects with shared design foundations. The accompanying test regimen defines how each project must be demonstrated in the game. The work-order plan defines sequencing and the information required before assigning implementation.

The team workflow records delegation, worktrees and continuity. The inferred-design policy is now required reading for missing states: the user directs the team to infer them from the concept's established patterns without repeatedly seeking approval for routine details. Exact source matching governs shown states; documented design consistency and functional parity govern inferred states. Neither class may silently weaken the other.

Evidence labels used throughout:

  • M — measured: a coordinate, count or decoded RGB value from a named source raster.
  • O — observed: a shape, arrangement or interaction visible in the source.
  • E — estimated: a plausible reconstruction parameter, including radii or nominal font size, still requiring comparison.
  • U — unresolved: not uniquely recoverable from available evidence, or not yet verified frame by frame.
  • R — required: a functional or engineering requirement for the mod; it is not presented as the designer's documented behavior.

Pixel equality means identical UI pixels at an explicitly fixed resolution, scale, data state and capture environment. It does not mean that a different colony map, pawn, language or monitor scale will produce the same screenshot. B01 and B04 are presentation boards: their blue grids, captions, outside margins and arrangement of several windows are excluded from the mod. B03's step-by-step banner is explanatory artwork, not a game toolbar. The film's closing title is also presentation material.

The original save, camera state and fully separated UI layers behind B02 are unavailable. Therefore, a full-screen zero-difference claim against B02 is currently impossible. UI regions can be reconstructed and compared; a whole-scene demonstration needs a matching fixture or a documented separation of UI from scene pixels. This limitation must never be hidden with an expansive ignore mask.

The ranges above are not final font sizes. Unscaled glyph crops — local evidence omitted are provided. Resolve typography as its own project before panel-by-panel implementation:

  1. Collect alphabets from the source, including the distinctive forms of a, g, R, 1, 4, %, punctuation, apostrophes and arrows. Separate regular, bold and micro-heading samples.
  2. Render candidate fonts at fractional and integer sizes. Compare glyph outline, advance width, x-height, cap height, baseline, kerning, line height and weight. Use multiple words; matching a single word is insufficient.
  3. Freeze a text-style table and the native asset identity/provenance available from the installed game. The user's later direction restricts this work to existing game fonts: do not create, download or bundle fonts or reconstruct glyphs. Record an unavailable raw font-file hash as unknown with its reason. If no existing candidate matches, retain the measured mismatch and continue calibration; do not silently accept a near match.
  4. Validate the actual Unity text path. The same font can differ through hinting, subpixel placement, atlas behavior, filtering or gamma. Use the existing native font rendering path under the current scope; text must remain data-driven, with glyph fallback for characters outside the canonical scene. A matching resource/fallback name alone does not establish exact glyph identity.
  5. Specify overflow per control: ellipsis, wrapping, clipping, scrolling or expansion. Preserve the reference baseline and padding. Do not shrink every string until it fits.

2.3 Surfaces and component geometry

The visible design uses several radii, not one universal rounded rectangle. E: tiny buttons/tags approximately 3–4 source pixels; compact HUD containers around 12 pixels; larger menu/comparison containers around 16 pixels; pawn panels around 20 pixels. These must be fitted against corner crops at the original scale, including antialiased edge coverage. Presentation-board corners are much larger and are excluded.

Common construction is outer shell → content inset or header → hairline separator → button/card → icon/text. Panels often have nearly opaque dark centers. U: whether a specific panel uses opacity, a shadow, or a darker underlying layer. Flattened artwork cannot uniquely solve observed = alpha × foreground + (1 − alpha) × background when both alpha and foreground are unknown. Multiple backgrounds or a deliberately chosen reconstruction recipe are needed.

User override, 18 October 2026: every window/panel must animate in and contract out, including nested/secondary windows, and have a slightly translucent background. This is an explicit product rule independent of uncertainty in flattened source art. Opening and closing both need validation; paint opacity must be effective after all backing layers are considered. Existing unconverted surfaces remain coverage gaps, not implied exceptions. See DEC-060 and the extension policy.

Primitives must expose independent parameters for face, border sides, corner coverage, inset, outer shadow, selected state, icon tint and text. Nine-slice borders must preserve corners and one-pixel rules rather than stretching a screenshot of a labeled button. Source positions must map consistently into screen pixels; changing UI.scale is not permission to improvise spacing.

3. Visual comparison procedure

3.1 Source preparation

  1. Verify source SHA-256 values against source-manifest.json.
  2. Define a reference-region record: source ID, exact crop, nominal component origin, scale calibration, component/state ID and evidence class.
  3. Trace the component's opaque/edge region. Exclude surrounding blueprint/caption/map pixels only with an explicit source mask. Never mask the UI border, icon, text, gradient, clipping edge or error area.
  4. Resolve layer ambiguities, fonts and source contradictions relevant to that state. If unresolved, record the state as incomplete rather than inventing an exact token.
  5. Freeze a canonical capture configuration and data fixture before first acceptance.

3.2 Capture protocol

Launch the test build in the isolated environment. Load the fixture, set the exact camera/UI state, pause simulation if appropriate, freeze UI timestamps/animations only through the test harness and put the pointer at a recorded position. Wait for assets/fonts to be ready and layout to settle. Capture lossless PNG from the game render target or a verified client-area capture path.

For a hover test, the pointer must be in a documented hit region. For a normal-state test, move it away without triggering another surface. For motion, capture an ordered series at fixed event-relative times without freezing the transition. Record the actually presented frame, not a delayed OS screenshot timestamp alone.

Save the full frame as well as the component crop. When using a development-only UI render target, capture RGBA or the UI against known backgrounds to diagnose compositing. The isolated output must use the actual game renderer, not an HTML recreation. Final proof includes the real full game screenshot.

3.3 Comparison and metrics

Use fixed coordinates. Do not auto-align, resize, blur, recolor or individually shift components before final comparison. These transformations hide spacing and glyph defects. A diagnostic registration preview may exist, but its transform must be disclosed and cannot be the acceptance comparison.

For each included pixel and RGB channel compute the absolute difference. Record:

  • Mismatched pixel count and fraction, with denominator equal to the included UI pixels.
  • Maximum channel error, mean absolute channel error and total error.
  • Separate mismatch counts for text, icons, panel faces, border/corner pixels and gradients.
  • Bounding box of differences and connected regions, plus geometry changes to anchors/baselines.
  • A raw difference PNG, amplified heatmap, 50/50 overlay and side-by-side source/result at 100% scale.

Exact static acceptance requires zero mismatched pixels in the agreed deterministic region. A diagnostic “within 1 RGB level” statistic may help find compression/rounding differences, but must not be relabeled as an exact match. Large flat backgrounds must not dilute a wrong icon or font into an impressive aggregate percentage.

Video comparison requires the same controls and event-relative states. Use frame indices and documented source frame rate where available. Never infer the frame rate solely from a duration ending in .916666. Obtain a clean frame sequence or record this measurement as unavailable. Compression, sampling and browser rescaling prevent claiming subpixel or millisecond certainty from the presently observed playback alone.

3.4 Review and baseline policy

The source PNGs are immutable. Approved game goldens are versioned separately and identify the source evidence they implement. A feature change never automatically regenerates goldens. Every changed golden requires a visible before/after/diff and a reason tied to a specification change or corrected implementation.

Shared typography, icons, primitives, scale transforms or GUI state changes invalidate every dependent golden. Re-run those states before merging or installing the change. A change limited to search sorting does not require unrelated glyph measurements again, but it does require search, navigation and live-selection regression.

5. Tests below the screenshot layer

5.1 Data and behavior tests

Use focused tests for real decisions: comparison ordering and stat direction, resource trend calculations across insufficient history, work-priority conversion and round-trip, grouping lifecycle, save filtering/selection identity, thought novelty, search invalidation, date/number formatting and settings migrations.

Avoid tests that merely duplicate a rectangle formula and assert its own output. Geometry tests must instead establish meaningful constraints: no forbidden overlap, all hit targets inside the declared panel, scrolling excludes clipped rows, and one coordinate maps to no more than one actionable foreground control.

5.2 Input and GUI-state tests

5.3 Persistence and save integrity

Byte-identical saves are not a valid expectation after advancing simulation; test semantic fields and separately check that untouched original fixture files remain untouched.

Test bad/missing settings, obsolete pawn IDs, deleted groups, corrupt trend history and conflicting mod IDs. Failure should leave the game usable and produce a clear single diagnostic rather than continuous exceptions.
